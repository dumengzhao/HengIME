# M0.5 三问之三：RIME 前端行为差异清单

> 目的：量出**路线 P（core 前置）的天花板**——哪些行为差异是配置能抹平的，
> 哪些是焊死在前端代码里、必须 core 亲自接管才能统一的。
> 依据：四前端源码浅克隆（`third_party/src/`，gitignored），引用均为 file:line。
> 检出版本：克隆日期 2026-10-03（master HEAD）。

## 1. 总对照表

| 维度 | Weasel (Win/TSF) | Squirrel (mac/IMK) | fcitx5-rime (Linux) | Trime (Android/IMS) |
|---|---|---|---|---|
| 会话粒度 | 每客户端一个 librime 会话 | 每客户端一个会话 | fcitx5 会话池，策略可配 | 服务级单会话 + 多客户端附加会话 |
| ascii_mode 记忆范围 | 默认会话独立；`global_ascii` 全局同步 | 仅会话级，无跨客户端传播 | 三档策略：No/Program/All | 键盘级 + 焦点切换重置项 |
| 按应用初始选项 | `app_options/<exe>` | `app_options/<bundle-id>` | 无（fcitx5 程序策略代偿） | 无（键盘/主题级配置代偿） |
| 记忆机制归属 | **前端代码**（handler 遍历会话） | **前端代码**（无传播） | **宿主框架**（PropertyPropagatePolicy） | **前端代码**（键盘状态机） |
| 跨重启记忆 | 无 | 无 | 无 | 无 |

## 2. 关键差异的源码证据

### 2.1 Weasel：开关传播是 handler 里手写的会话遍历

- `weasel.yaml` 的 `global_ascii` 开关被读进 handler：
  `RimeWithWeasel.cpp:137-139`（`config_get_bool("global_ascii", &global_ascii)`）。
- 新会话建立时，从任一已有会话**拷贝** ascii_mode：
  `RimeWithWeasel.cpp:174-182`（`AddSession` 里 `set_option(session_id, "ascii_mode", ...)`）。
- 用户切换 ascii 时，遍历**全部**会话逐个 `set_option` 广播：
  `RimeWithWeasel.cpp:494-504` 与 `778-783`（`m_global_ascii_mode && opt == "ascii_mode"` 分支）。
- 按应用初始选项：焦点变化时 `set_property(session, "client_app", app_name)`
  （`RimeWithWeasel.cpp:425-432`），再从 `app_options/<app>` 取初始值应用（`434-440`、`624-640`）；
  加载处 `_LoadAppOptions`（`1422-1428`）。
- 无持久化：重启后所有会话回到方案默认值（源码中无 set_option → 磁盘的写回路径）。

### 2.2 Squirrel：完全没有跨会话传播

- ascii 只在单会话上 get/set：`SquirrelInputController.swift:193`、`:625`、`:633`。
- 按应用初始选项：`SquirrelConfig.swift:103`（rootKey = `app_options/<bundle-id>`），
  默认配置给 Terminal 等应用 ascii_mode: true（`data/squirrel.yaml:393-401`）。
- 唯一的"全局"是给命令行的查询口：DistributedNotificationCenter 广播
  `SquirrelASCIIModeResponse`（`SquirrelInputController.swift:629-640`），不是输入状态传播。
- 同样无跨重启记忆。

### 2.3 fcitx5-rime：粒度控制委托给宿主框架

- 策略枚举 `SharedStatePolicy = { FollowGlobalConfig, All, Program, No }`
  （`rimeengine.h:57`），配置项 `InputState`（`rimeengine.h:85-87`），**默认 All**。
- 映射到 fcitx5 的 `PropertyPropagatePolicy`（`rimeengine.cpp:770-782`），
  由 fcitx5 会话池执行状态传播（`rimeengine.cpp:762-768`）。
- **关键点**：这不是 librime 的能力，而是宿主框架的属性传播机制。
  换宿主（TSF/IMK/IMS）时这套粒度控制必须在前端重写——这正是配置级统一的天花板。

### 2.4 Trime：粒度单位从"应用"变成"键盘"

- 键盘可配自己的 ascii 初值：`Keyboard.kt:83-85`（`asciiMode = selfConfig?.asciiMode == 1`）。
- 切键盘时按 `resetAsciiMode` 决定回初值还是记上次的 `lastAsciiMode`
  （`KeyboardWindow.kt:175-189`）。
- 主题级开关 `reset_ascii_mode_on_focus_change`（`data/theme/model/GeneralStyle.kt:149`）。
- 会话模型不同：`RimeDaemon.createSession(name)` 是共享 daemon 上的多客户端会话，
  IME 服务本体只建一个（`TrimeInputMethodService.kt:185`），同步/设置界面各建各的
  （`BackgroundSyncWork.kt:48`、`MainViewModel.kt:17`）。

## 3. 对路线 P 的含义（天花板在哪、多厚）

1. **开关记忆语义不在 librime 里，而在四份前端代码里，且四份互不相同。**
   路线 P 若要"五端行为统一"，必须把这件事上收到 core：
   core 需要新增（IDL 层面）：
   - `SetSessionOwner(app_id)` —— 对齐 Weasel/Squirrel 的 `client_app`/`bundle-id`；
   - 开关传播策略（`global | per-app | per-session`）—— core 统一实现，
     各端外壳只剩透传，不再各自手写遍历；
   - `app_options` 表的统一加载与应用时机（焦点变化时）。
2. **工作量估计：薄。** Weasel 的实现总共约 60 行 C++（拷贝 + 遍历 + 应用），
   core 侧一份实现替换四份；难点不是代码量，而是**语义对齐**——
   Android 没有"应用焦点"事件流（Trime 用键盘粒度代偿），
   IMK/IMS 的客户端生命周期与 TSF 不同，`SetSessionOwner` 的触发时机要逐端适配。
3. **fcitx5 是特例**：Linux 上传播机制在宿主框架里，路线 P 等于绕过它自建一份
   （或让 Linux 前端继续用 fcitx5 机制 → 违反统一命题）。决策门时按"core 自建"计。
4. **跨重启记忆四端都没有**——core 接管后反而可以免费获得（选项写 user.yaml），
   这是统一带来的增强项而非兼容负担。

## 4. 结论

- 差异是**机制性**的（谁持有状态、传播到哪），不是参数性的 → **配置级统一不成立**，证实第 5 条已焊死结论。
- 但机制的**实现成本很小且高度可归纳**（一个 owner 概念 + 一个传播策略 + 一张 app_options 表）。
- M0.5 裁决时，此清单与薄壳化试验、Slint 窗口属性试验并列作为路线 P vs F 的输入。
