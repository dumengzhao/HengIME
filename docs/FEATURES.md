## 0. 跨端统一约束

以下四条是所有功能需满足的约束，不属于功能项。任一功能在某端表现不同即为缺陷。

1. **行为一致**：组词、候选排序、翻页、开关语义、方案切换在五端相同。
2. **视觉一致**：候选窗与设置窗均由 core 自绘，不使用宿主框架渲染。
3. **设置一致**：配置读写集中在 core，UI 层不含配置知识。
4. **数据一致**：词库、用户词频、配置真源在五端共享，依赖 §4 的同步能力。

## 4. 账号与服务端（⬜ **本清单的重点待办**）

**为什么排进清单而不是随手做**：这是「五端统一」里唯一还没着落的一环。没有它，
「同一份数据」只是文件共享（用户得自己用网盘同步目录），不是产品级体验。

| 功能 | 状态 | 说明 |

### 已有基础

- **`heng_sync_user_data()`**（`core/src/capi.rs`）—— librime 的 sync 机制，
  导出带 `#@/tick`、`#@/user_id` 头的**文本快照**。
- librime 的 sync 不含网络代码：只把快照写到一个目录；未配 `sync_dir` 时
  默认落到 `user_dir\sync\<installation_id>\`，为本地镜像。跨设备依赖网盘/U盘。
- 因此服务端方案的流程是：**客户端导出快照 → 上传 → 服务端存文件 →
  合并 tick → 其他端拉取**，传输层需要自己实现。
- 设置页无「用户资料同步」入口（与本节范围重叠）；ABI 侧的 `heng_sync_user_data`
  保留且当前无调用方。

### 设计时要回答的问题

- [ ] 自建服务 vs 用现成云（BaaS 托管）—— 自用不上架，倾向于最小成本
- [ ] 快照合并策略：同 `user_id` 不同 `tick` 怎么合（先到先得 / 按 tick 取大 / 服务端做三方合并）
- [ ] 频率与触发：手动 / 退出时 / 定时？输入法不该有常驻轮询
- [ ] 认证范围：只同步数据，还是也要同步开关记忆（架构已知天花板，见 `ARCHITECTURE.md`）
- [ ] 五端各自的 user_dir 路径不同 → core 需暴露统一的同步目录
