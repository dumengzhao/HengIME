# M0.5 三问之一：薄壳化试验（Weasel 案例）

> 试验问题：把现成前端的候选窗/前端数据源换成 heng-core，是「改造」还是「重写」？
> （全项目最大的未验证假设，docs/ARCHITECTURE.md 第 9 章）
> 对象：Weasel（小狼毫，Windows 参考实现），源码 `third_party/src/weasel/`。
> 方法：实测各层对 librime 的依赖面 + 数据流边界 + 接口映射。日期 2026-10-03。

## 1. 实测结论先行

**Weasel 本身已经是「薄壳 + 服务进程」架构，前端与引擎之间隔着纯数据结构。
换数据源 = 改一个类（或实现一个管道协议端），不是重写。**

三层依赖实测（grep 全源码）：

| 层 | librime 依赖 | 数据来源 | 证据 |
|---|---|---|---|
| WeaselTSF（TSF 前端） | **零**（仅注释/注册表路径字样） | `weasel::Client` IPC 接口（16 个方法） | WeaselTSF/ 全目录 grep `rime_api|RimeApi` 无匹配 |
| WeaselUI（候选窗渲染） | **零** | `weasel::Context/Status/UIStyle` 纯数据结构 | WeaselUI/ 全目录 grep 无匹配 |
| RimeWithWeasel（服务端） | **唯一**摸 librime 的层 | 直接调 `rime_api->` | RimeWithWeasel.cpp 全部引擎调用集中于此 |

数据流：

```
应用进程                          服务进程 (WeaselServer.exe)
┌─────────────┐   命名管道    ┌──────────────────────────────┐
│ WeaselTSF   │ ───────────▶ │ WeaselServerImpl             │
│ (零rime依赖) │  weasel::    │   └ RimeWithWeaselHandler ───┼──▶ librime
└─────────────┘  Client 16法  │      （唯一 rime 触点）        │
┌─────────────┐              │ WeaselUI（零rime依赖）◀───────┤
│  候选窗渲染  │◀── 同协议 ────│  吃 Context/Status/UIStyle   │
└─────────────┘              └──────────────────────────────┘
```

## 2. 关键数据结构（纯数据，boost 序列化过管道）

`include/WeaselIPCData.h`：

- `weasel::Context` = `preedit: Text` + `aux: Text` + `cinfo: CandidateInfo`
- `weasel::CandidateInfo` = candies/comments/labels（三个平行 `vector<Text>`）+
  currentPage / is_last_page / highlighted / totalPages
- `weasel::Status` = schema_id/schema_name/ascii_mode/composing/disabled/full_shape
- `weasel::UIStyle` = 主题/布局参数（~60 字段，与引擎无关）

## 3. weasel::Client 接口 ↔ heng-core 映射

`include/WeaselIPC.h` 的 Client 16 法 vs heng-core（C ABI + HTTP）：

| weasel::Client | heng-core 现状 |
|---|---|
| Connect / Echo / StartSession / EndSession | ✅ heng_create / POST+DELETE /api/sessions |
| ProcessKeyEvent | ✅ heng_process_key / POST keys |
| CommitComposition | ✅ heng_commit_text / GET commit |
| ClearComposition | ✅ heng_clear / POST clear |
| SelectCandidateOnCurrentPage | ✅ heng_select_candidate_on_current_page / POST select |
| GetResponseData（拉回 Context+Status） | ✅ GET context / status |
| FocusIn / FocusOut / UpdateInputPosition | ⚠ core 无对应（会话归属语义，M0.5-Q3 已论证需 SetSessionOwner） |
| **HighlightCandidateOnCurrentPage** | ❌ **core 缺**（librime 有同名 API，rime_ffi 未转录） |
| **ChangePage** | ❌ **core 缺**（librime 有 `change_page`） |
| TrayCommand / Start/EndMaintenance | 部署器/托盘专属，不在热路径 |

**16 个方法里 10 个已覆盖，缺 3 个热路径方法（Highlight/ChangePage/归属事件）**——
全部是 librime 现成 API 的透传，core 侧增量约半天。

## 4. 字段级映射（librime → weasel::Context，已有人写好的范本）

`RimeWithWeasel.cpp:_GetCandidateInfo()`（454-473 行，共 ~25 行）就是把
`RimeContext` 填成 `CandidateInfo` 的转换器，与 heng-core 的 `HengContext`/`ContextSnapshot`
逐字段重合：

| weasel::CandidateInfo | librime 来源 | heng-core 对应 |
|---|---|---|
| candies[i].str | menu.candidates[i].text | ✅ candidates[i].text |
| comments[i].str | menu.candidates[i].comment | ✅ candidates[i].comment |
| labels[i].str | select_labels / select_keys / 序号 fallback | ⚠ core 只有 select_keys 一路，缺 select_labels（RIME_STRUCT 版本化成员） |
| highlighted | menu.highlighted_candidate_index | ✅ highlighted |
| currentPage / is_last_page | menu.page_no / menu.is_last_page | ✅ page_no / is_last_page |
| totalPages | 由调用方算 | ✅ 可由 page 数据推导 |

preedit/aux/Status 同理全部可映射，无结构性障碍。

## 5. 「改造」的两条落地路径

**路径 A：heng-server 实现 Weasel IPC 协议（TSF/UI 二进制零改动）**
- 命名管道（`PipeChannel`，管道名派生自安装配置）+ boost 序列化 wire 格式；
- core 侧新增一个「weasel 协议端」：收 16 消息 → 调 engine → 按 weasel wire 格式回包；
- 工作量：wire 格式对齐（boost serialization 文本格式）+ 管道服务，约 2-3 天；
- 风险：boost 序列化格式逆向对齐、版本兼容；收益：**WeaselTSF.dll 原样可用**。

**路径 B：重编 WeaselServer，替换 RimeWithWeaselHandler 数据源为 heng-core C ABI**
- 只改 `RimeWithWeasel/` 一个目录：把 `rime_api->` 调用换成 `heng_*` 调用（映射表见 §3/§4）；
- WeaselTSF / WeaselUI 源码与二进制**都不用动**（协议与数据结构不变）；
- 工作量：一个 handler 类的改造（~10 个调用点）+ Weasel 编译环境，约 2-4 天；
- 风险：Weasel 构建链（boost/MSVC）；收益：直接得到可日常使用的 Windows 外壳。

## 6. 改造 vs 重写 量化对比

| 方案 | 改动范围 | 估计工作量 | 失去 Weasel 既有能力 |
|---|---|---|---|
| **改造**（A：协议兼容） | 新增协议端，零改 Weasel | 2-3 天 | 无（但受 wire 格式牵制） |
| **改造**（B：换 handler） | 1 个目录 / ~10 个调用点 | 2-4 天 | 无 |
| **重写**（自写 TSF + UI） | TSF 前端（register/keysink/composition 全套）+ 候选窗渲染 + IPC | 数周起 | —— |
| **采纳 Weasel 直接用** | 0 | 0 | 放弃五端统一命题 |

**结论：改造是重写的 1/5 以下成本，且 WeaselTSF/WeaselUI 与 librime 的解耦是
架构性保证（不是巧合），数据源可替换性成立。**

## 7. 对决策门的最终推论（Q1+Q2+Q3 汇总）

1. **薄壳化假设成立**（Q1）：Weasel 实证「TSF 薄壳 + 服务进程 + 数据驱动 UI」可改造，
   heng-core 只需补 3 个 API + 会话归属语义即可对齐前端需求；
2. **L2 候选窗无阻断**（Q2）：Slint + 薄 shim 真机验证通过；
3. **core 需上收开关语义**（Q3）：SetSessionOwner + 传播策略 + app_options，
   实现成本薄（Weasel 的实现仅 ~60 行 C++）。

**路线 P（core 前置）与路线 F 的选择建议**：证据全面倒向路线 P——
改造 Weasel（B 路径）即可先得到 Windows 成品，同时 heng-server 作为唯一引擎宿主，
其他四端复制「薄壳接协议」模式。剩余决策项只剩：是否接受 Weasel 编译链作为 M1 前的
过渡外壳（vs 直接自写 TSF）。
